# Phase 2 — реализация и проверка

Выполнено 2026-09-06. Все пункты Phase 2 из PROJECT_SPEC.md реализованы. Реальные источники и сетевое получение их изображений остаются Phase 4; пользователь ранее подтвердил разрешения.

## Обработка

Worker получает NormalizedListing, готовит pHash до транзакции записи и передаёт fingerprints в ingestion. Изображения не скачиваются произвольным HTTP клиентом: текущий mock использует конечный список `mock://panamera|bmw|other/0..5` и собственные детерминированные синтетические рисунки. Это тестовые изображения, а не фотографии реальных машин; в карточках остаётся заглушка фотографии. `PHashProvider.fingerprint(image_id, bytes, stock=...)` принимает байты для будущего транспорта источника. Интерфейс FingerprintProvider выделен отдельно; embedding backend пока отсутствует.

Pillow 12.3.0 нормализует EXIF-ориентацию. DCT 32×32 → 64 бита имеет собственную версию `phash64-dct32-pillow12.3-v1`. Ограничения: максимум 6 изображений, 8 MiB на изображение, 16 миллионов пикселей, сторона не меньше 64. Пустые, битые, слишком большие и помеченные адаптером как stock изображения исключаются; универсального распознавания stock-фото нет. Hash разных версий/алгоритмов не сравнивается. Внутренние повторы удаляются консервативно по расстоянию pHash. Максимальное взаимно однозначное соответствие выбирается динамическим программированием, затем минимизируется суммарное расстояние. Копии одной картинки не увеличивают число совпадений.

Кандидаты ограничены memberships текущего пользователя, make/model, допустимыми year/mileage и горизонтом снятых объявлений. При неизвестных make/model полного перебора нет. Цена не отсекает кандидата. Город/регион и совпадающие характеристики влияют на порядок; лимит записывается в evidence как `candidate_limit_hit`. Известные противоречия остаются в объяснении и запрещают автоматическую склейку.

Score сохраняет отдельно недоступный сигнал и нулевое сходство; отсутствующие фото не перераспределяют вес на характеристики. Внутри specifications используются равные веса 11 полей, внешние веса и допуски конфигурируются. Rare features пока недоступен, его вклад равен нулю. Текст — пересечение/объединение непустых токенов после удаления контактов/URL; разбор шаблонных блоков реальных площадок относится к нормализаторам Phase 4. Порог не является измеренной вероятностью. Произвольная обрезка, сильные водяные знаки и реальные ложноположительные случаи требуют отдельной калибровки.

## Транзакции и сохранность решений

Миграция `00af18fb3260` добавляет listing_fingerprints, duplicate_candidates, duplicate_decisions, cluster_operations, relist_links и поля состояния/архива кластеров. Канонические пары `left_id < right_id` имеют составные внешние ключи на пользовательские memberships. Активное ручное решение уникально; замена заполняет superseded_at старой записи и добавляет новую, история не переписывается.

Ingestion и ручные операции берут advisory lock пользователя, операции проверяют ожидаемые версии кластеров. Перед merge все участники читаются под блокировкой Listing в стабильном порядке с NOWAIT. При параллельном обновлении — 409/ручная проверка, без ожидания с риском взаимной блокировки. Автоматический сильный сигнал повторно вычисляется на актуальных сохранённых полях/fingerprints под блокировкой. Проверяются все межгрупповые запреты и противоречия; A≈B≈C не обходит ручное A≠C. На одну операцию максимум 100 объявлений.

Merge архивирует опустевшие исходные кластеры, сохраняет минимальное пользовательское first_seen, OR избранного/скрытия и все заметки. Split требует полного разбиения без повторов/пропусков, архивирует исходный кластер, создаёт новые и запрещает пары между группами. UI предлагает разложить на отдельные объявления; произвольное разбиение поддерживается API. Редактирование заметок и избранного остаётся Phase 3, но перенос состояния покрыт тестами. Аудит хранит прежний/новый состав и основания. Существующие Listing/snapshots не удаляются.

Вероятное перевыставление связывается только при REMOVED, подтверждённом до первого наблюдения нового ACTIVE объявления, в пределах окна 365 дней, с сильной связью или ручным same. Транзитивная автоматическая склейка не создаёт relist для неподтверждённых рёбер. Global Listing остаётся REMOVED, персональная карточка показывает RELISTED. Split удаляет утратившие основание персональные relist-связи с записью их IDs в аудит; историческое событие остаётся. PRICE_DROP старой карточки из снижения цены нового объявления не создаётся.

## API

Все операции требуют сессию; запись также требует Origin и X-CSRF-Token.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/duplicates?search_id=UUID&limit=30` | До 30 пар для проверки, explanation, актуальные cluster IDs/версии, has_more |
| POST | `/api/vehicles/merge` | `{ "versions": { "cluster UUID": 1, "other UUID": 2 }, "supersede_rejections": false }` |
| POST | `/api/duplicates/reject` | versions ровно двух групп; запрет всех пар между ними |
| POST | `/api/vehicles/{id}/split` | `{ "version": 1, "groups": [["listing UUID"], ["other UUID"]] }` |
| GET | `/api/vehicles?search_id=UUID` | Одна карточка на кластер, cluster_version, число подходящих объявлений, курсор по кластеру |
| GET | `/api/vehicles/{id}` | Состав, версия, snapshots, matching evidence, ручные решения и relist-связи |

Чужой ID даёт 404. Устаревший/архивированный собственный кластер, занятые объявления или конфликт решения дают 409. Некорректное разбиение — 422. Замена different на same требует явного `supersede_rejections=true`; в UI это отдельный подписанный переключатель. Пары выдаются ограниченной очередью: после обработки показанных подгружаются следующие; полноценная навигация review остаётся Phase 3.

`MATCHING` в `.env` — JSON с переопределениями MatchingConfig, например:

```dotenv
MATCHING={"auto_merge_threshold":0.9,"candidate_limit":100}
```

Настройки проверяют веса/пороги/лимиты. Config version — стабильный digest полного конфига; он сохраняется с результатом. Для применения перезапустите API/worker. Изменение порога не отменяет ручные решения и само не пересобирает все старые кластеры; повторная оценка выполняется при очередном ingestion.

## Проверки

- **43 теста прошли** на настоящем PostgreSQL 17.11: пять основных сценариев, идемпотентность, изоляция пользователей, API/CSRF из Phase 1, фото, null/zero, границы порогов, ограниченная выборка, повторный matching после split и смены порога, сохранение состояния, параллельные merge и обновление объявления.
- Реальные преобразования пяти собственных рисунков: resize, JPEG quality 45, небольшой watermark, crop по 4–5 пикселей; проверяется pHash distance ≤8 для этих fixtures, без обещания универсальной устойчивости.
- Новая миграция применена к локальной рабочей БД без удаления данных. Downgrade к 0001_core / upgrade выполнены **только на findcar_test**. Alembic check: различий нет.
- Backend Ruff/mypy и frontend TypeScript/ESLint/build прошли.
- В Codex IAB проверены возможная пара → объяснение → reject → явная замена решения → manual merge и просмотр состава. Найденная ошибка повторяющихся React keys устранена.
- Снимки IAB были недоступны (`Unable to capture screenshot`). Browser plugin/skill в сессии отсутствовал; визуальная проверка выполнена локальным Playwright с уже установленным Edge, без установки нового браузера. Проверены desktop 1505×1045, mobile 390×844, подробности и split → три карточки. Горизонтального переполнения нет, ошибок после входа нет. Первоначальный 401 `/api/auth/me` до входа ожидаем; отсутствовавшая favicon добавлена.
- Docker Compose config проверяется отдельно; контейнеры по-прежнему не запущены из-за недоступной виртуализации на машине. Локальные API/worker/PostgreSQL/Vite работают.

Следующий этап — Phase 3, полный Frontend MVP. Реальные источники, сетевые image budgets, долгие задания и расписание не входят в выполненную Phase 2.
