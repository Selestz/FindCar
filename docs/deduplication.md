# Дедупликация без VIN

Статус: алгоритм реализован в Phase 2; конкретные решения и границы — [phase2.md](phase2.md). Калибровка на реальных данных ещё не проводилась. Цель — избегать ложной склейки; пропущенный дубль можно показать для ручной проверки. Значения ниже — начальные настройки проекта, не измеренная точность.

## Вход и границы

Сравниваются NormalizedListing и сохранённые fingerprints. Не используем HTML, source_metadata, телефоны и обязательный VIN. Каждое новое объявление сначала попадает в отдельный пользовательский VehicleCluster, затем может быть объединено.

Слой fingerprints реализует `FingerprintProvider.fingerprint(image)` и `compare(a,b) -> PhotoSignal`. Тип результата содержит algorithm/version/quality; pHash можно дополнить embedding provider без изменения кластеризации. Нельзя сравнивать байты разных алгоритмов как один hash.

## Этап A: кандидаты

1. Выбрать только объявления из кластеров текущего пользователя; среди них и снятые — для перевыставления.
2. При известных make/model требовать совпадения canonical keys; year ±1. При неизвестной марке/модели не делать полный перебор: insufficient_evidence до обогащения карточки или ручного решения.
3. Известные несовместимые generation, engine_type, body_type отсекают кандидата либо становятся veto. Nullable generation не является несовпадением.
4. Пробег: разница не более `max(absolute_tolerance, relative_tolerance * max(mileage_a,mileage_b))`; неизвестный пробег не отбрасывает кандидата. География, цвет, объём двигателя и мощность ранжируют кандидатов, но один пропуск или возможная ошибка площадки не запрещает ручной review.
5. Сначала тот же город/регион, затем допустимые другие регионы в пределах общего лимита. Перемещение машины возможно; регион не абсолютная идентичность. Цена вообще не участвует в обязательном SQL условии.
6. Упорядочить по числу согласующихся характеристик, близости пробега и ID; взять максимум 100 кандидатов. Флаг candidate_limit_hit виден диагностике; это не доказательство отсутствия дублей за пределами выборки.

Запрос использует индексы из database.md, без cross join всей базы. Старые снятые объявления рассматриваются в окне relist 365 дней от последнего подтверждённого наблюдения; горизонт configurable. При отсутствии фото/полей отложенная обработка может повторно оценить пару после detail/enrichment.

## Этап B: фото

Получаем до шести фото в допустимом source budget; full-size архив не сохраняем. После нормализации ориентации вычисляем 64-bit pHash; dHash можно добавить как дополнительный сигнал. Для технической реализации рассматривается [ImageHash](https://github.com/JohannesBuchner/imagehash); версия библиотеки и параметры должны быть закреплены в fingerprints и fixtures.

Сначала удаляем дубли фотографий внутри каждого объявления. Затем строим пары с Hamming distance ≤ phash_distance_threshold и ищем максимальное взаимно однозначное соответствие. Одна фотография или её копии не могут дать пять совпадений. Учитываем несколько разных ракурсов; однотонные/пустые изображения и известные шаблонные dealer stock photos не считаем сильным сигналом.

Сигнал фото: `matching_count`, пары с distances и IDs, score по качеству совпадений, доступное количество уникальных фото, quality_flags. Начальный photo score — среднее `1 - distance/64` по подобранным парам, умноженное на `min(1, matching_count/minimum_matching_photos)`. Если обе стороны содержат достаточно качественных фото и ни одной пары нет, score=0 и strong_photo_signal=false. Если фото не удалось получить, score=null и причина недоступности; это отличается от доказанного отсутствия совпадений.

Пережатие/resize/crop/watermark проверяются на собственных synthetic fixtures. Устойчивость pHash к произвольному crop или watermark не обещаем. При слабом результате — review/неопределённость; не пытаемся компенсировать его одной маркой и цветом. Совпадение шаблонных фотографий также не доказывает идентичность автомобиля.

## Сигналы и score

Все similarity значения в диапазоне [0,1]. Отсутствие данных отражается availability, evidence_coverage и explanation.

| Сигнал | Начальный вес | Расчёт |
| --- | ---: | --- |
| photos | 0.60 | Несколько взаимно однозначных совпадений фото, формула выше |
| specifications | 0.22 | Согласованность известных make/model/generation/year/engine/power/transmission/drive/body/color; таблица внутренних весов конфигурируется |
| mileage | 0.10 | `max(0, 1 - abs(a-b) / max(absolute_tolerance, relative_tolerance * max(a,b)))` |
| description | 0.05 | Fuzzy token similarity очищенного текста; без контактов и шаблонных блоков, два пустых текста не дают 1 |
| rare_features | 0.01 | Только типизированные признаки; в MVP не дают самостоятельного разрешения на auto merge |
| price | 0.02 | `min(a,b)/max(a,b)` при положительных ценах в одной валюте; иначе недоступен |

Сумма весов 1. `total_score = sum(weight * signal_score)`; недоступный сигнал даёт 0 вклада, но сохраняет score=null в explanation. Не перенормируем отсутствующие фото на остальные сигналы, иначе одинаковые массовые автомобили получат искусственные 100%.

Для specifications сравниваем известные с обеих сторон поля; отдельно возвращаем долю покрытых характеристик. Минимальный набор auto merge: совпадают make/model и известен совместимый year; необходимые значения не выводятся из текста без normalizer. Сильное известное противоречие (другая марка/модель, несовместимый кузов/двигатель/поколение) блокирует auto merge даже при фото; review показывает конфликт.

## Решение

Порядок важен:

1. Активное manual different → different, независимо от score; active same → сохранить ручную связь, не запускать автоматический split. Противоречивые новые данные отображаются пользователю.
2. Auto merge только при score ≥ 0.88, strong_photo_signal (минимум 3 независимых совпавших фото), достаточных характеристиках, отсутствии veto и запретных пар во всех объединяемых кластерах. В MVP необычной комплектации самой по себе недостаточно.
3. Score ≥ 0.68 при отсутствии auto merge → possible_duplicate; ограничения/конфликты объясняются.
4. Если фото отсутствуют или их недостаточно, возможен отдельный review путь: совпадающие make/model/year, specifications ≥ 0.9, coverage характеристик ≥ 0.7, близкий известный mileage, без сильных конфликтов → possible_duplicate с причиной insufficient_photos. Низкий total_score остаётся исходным. Это нужно для CASE 4, поскольку отсутствие фото намеренно не компенсируется весами.
5. Если достаточно сопоставимых фото, но совпадений нет, одних стандартных характеристик недостаточно даже для автоматического review по правилу 4. Решение different означает «не объединять», а не доказанный факт о физической машине.
6. Остальные случаи: different при достаточных данных или insufficient_evidence при неполноте. UI не изображает недостаток данных как надёжное отрицательное заключение.

Варианты confidence — категориальные high/medium/low/insufficient_evidence. Score объясняет сходство, а не вероятность правильного вывода.

## Начальная конфигурация

```yaml
auto_merge_threshold: 0.88
possible_duplicate_threshold: 0.68
mileage_absolute_tolerance: 10000
mileage_relative_tolerance: 0.10
year_tolerance: 1
phash_distance_threshold: 8
minimum_matching_photos: 3
maximum_processed_photos: 6
candidate_limit: 100
relist_window_days: 365
review_specs_threshold: 0.90
review_specs_coverage: 0.70
weights:
  photos: 0.60
  specifications: 0.22
  mileage: 0.10
  description: 0.05
  rare_features: 0.01
  price: 0.02
```

Валидатор config проверяет сумму весов, упорядоченность порогов, положительные допуски и minimum_matching_photos ≤ maximum_processed_photos. Config/algorithm версии записываются вместе со score. Изменение порога не отменяет ручное решение и не запускает разрушительное переклеивание всей базы.

## Безопасная кластеризация

Нельзя делать безусловный union-find только потому, что A≈B и B≈C. Перед слиянием проверяем запреты и противоречия всех членов двух кластеров. Для нового члена нужен сильный match хотя бы с одним существующим членом и отсутствие явного конфликта с остальными. Если вторая часть проверки не завершена, только review. Сохраняются доказательства рёбер и audit состава.

Общие Listing не удаляются и не переписываются при merge: меняются пользовательские memberships. first_seen кластера — минимум времени первого наблюдения его объявлений в search_listings этого пользователя, а не более ранняя дата чужого поиска. События сохраняют исходный cluster_id_at_event, UI разрешает актуальный состав через membership/audit.

### Ручные операции

- Merge принимает IDs кластеров/объявлений текущего пользователя и ожидаемые версии. Уже отклонённую пару нельзя молча снова склеить: нужно явное новое решение, superseding старое. Все внутренние связи выбранных групп фиксируются как same.
- Reject фиксирует different для канонической пары listing IDs; если отвергаются целые кластеры, сохраняются запретные пары между группами. Обход через третий кластер запрещён.
- Split принимает явное разбиение полного множества выбранного кластера без пропусков/повторов. Для разных групп записываются different; пересекающие split старые same решения явно заменяются, с аудитом. Новые кластеры получают собственные ID, исходный архивируется.
- Состояния при merge: favourite и hidden объединяются OR; заметки не теряются, объединяются с датой и происхождением. При split favourite/hidden копируются, заметка копируется с пометкой «из исходного кластера», затем редактируется независимо. Операция выполняется только внутри пользователя.
- Auto merge никогда сам не переопределяет manual same/different. Все проверки повторяются внутри транзакции под блокировкой из database.md.

## Перевыставление

Новый source_listing_id проходит тот же matching, включая старые объявления. Чтобы создать PROBABLE_RELIST, нужны: другое ID; старое подтверждённо REMOVED до первого наблюдения нового; временное окно; сильная связь или ручное same. Без подтверждённого снятия это просто cross-post/duplicate, не relist. published_at не подменяется датой наблюдения.

Достаточный score связывает новое ACTIVE объявление с тем же пользовательским кластером; старое можно показывать как RELISTED только с подтверждённым основанием через персональную relist_links. Глобальный Listing сохраняет REMOVED, чтобы решение одного пользователя не изменяло состояние другого. Если данных меньше — possible_duplicate с гипотезой relist и без автосклейки. Снижение цены между старым и новым — часть relist timeline, не PRICE_DROP старой карточки.

Сохраняется связь old→new с evidence, пользователем, config/version и причиной. Дата самой ранней известной продажи не объявляется фактической датой начала продажи до появления в системе.

## Проверки Phase 2

| Сценарий | Ожидаемое поведение |
| --- | --- |
| CASE 1: Panamera, пять разных совпадающих фото, пробег +1000 км, согласующиеся характеристики | Auto merge; explanation содержит 5 пар, разницу км и версию score |
| CASE 2: две чёрные BMW 320i одного года, близкий пробег, разные качественные фото | Не merge |
| CASE 3: старое подтверждённо снято, новое через месяц, ≥3 совпавших фото, +3000 км, −100000 ₽, остальные сигналы достаточны | Тот же кластер и PROBABLE_RELIST; при 1–2 фото только review |
| CASE 4: характеристики почти одинаковы, фото недостаточно | Possible duplicate через отдельный review путь, auto merge запрещён |
| CASE 5: manual different | Автосклейка запрещена после рестарта/смены порога и через третий кластер |
| Одна фотография повторена шесть раз | matching_count=1, сильного сигнала нет |
| Фото stock/однотонное/битое/слишком большое | Исключение из сильного сигнала; загрузка ограничена, корректная причина |
| Совпавшие фото, но известны несовместимые модели | Veto auto merge, конфликт явно показан |
| A≈B, B≈C, A explicitly different C | Нельзя объединить три кластера |
| Два пользователя по-разному решили одну пару | Независимые memberships/notes/events |
| Пропажа с первых страниц, timeout или CAPTCHA detail | Нет LISTING_REMOVED и ложного relist |
| Повтор ingestion/worker retry и split→повторный matching | Нет повторных событий/дублей и отмены ручного split |

Проверять реальные преобразования собственных синтетических изображений (resize, JPEG quality, watermark, небольшой crop), а не только заранее заданные числа hash. Отдельно проверять границы порогов, missing-vs-zero, симметричность pair scoring, неизменность manual decisions и транзакционные гонки на PostgreSQL.
