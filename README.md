# FindCar

## Полнота и актуальность поиска

Обход теперь продолжается с сохранённой страницы: по умолчанию 5 страниц за проход до глубины 50. Drom фильтрует годы на площадке и поддерживает 14 городов. Избранное проверяется приоритетно, карточки показывают время фактической проверки, а выдача — степень покрытия. Бюджет запросов сохранён. Подробности и ограничения: [полнота поиска](docs/search-coverage.md).


Приватный поиск автомобилей для небольшой группы пользователей. Требования — [PROJECT_SPEC.md](PROJECT_SPEC.md).

**Развёрнуто на [testerio.ru](https://testerio.ru/) 2026-09-07.** Docker Compose, PostgreSQL, API, worker и HTTPS проверены на VPS; 107 тестов прошли внутри контейнеров. По запросу пользователя создана новая база без переноса локальных данных. Инструкции запуска, обновления и возврата прежнего проекта — [deploy/README.md](deploy/README.md).

## Текущий интерфейс и поиск

- Утверждённый вариант C: графитовый фон, фиолетовый акцент, крупные карточки в две колонки; на телефоне одна колонка и отдельная панель фильтров.
- Название поиска создаётся автоматически из условий. Марки и модели выбираются из справочника с поиском: 73 марки и 3 736 моделей. Годы и цены — списки с поиском; цены идут с шагом 100 000 ₽.
- «Найти автомобили» сохраняет условия и запускает проверку. «Сохранить поиск» сохраняет без немедленного запроса; автообновление продолжает работать по расписанию. Сохранённые поиски доступны над результатами, расписание — под ними.
- В результатах, избранном и скрытых отображаются только активные предложения. Снятые объявления сохраняются в истории автомобиля; они не участвуют в актуальном диапазоне цен.
- Демо отключено: старые синтетические объявления, поиски и события исключены из рабочих экранов и API. Mock включается только явным флагом в изолированных тестах; Docker Compose всегда запускает рабочие сервисы с `TEST_FIXTURES_ENABLED=false`.

Описание изменения и проверок — [редизайн C](docs/redesign.md), происхождение справочника — [catalog/README.md](backend/app/catalog/README.md). Разделы фаз ниже сохраняют историю разработки; упоминания демо относятся к прежним версиям.

## Что работает в Phase 1

- FastAPI + PostgreSQL, явная миграция Alembic, отдельный worker без Redis.
- Закрытые аккаунты: Argon2id, HttpOnly session cookie, CSRF/Origin, ограничение попыток входа, CLI первого admin. Admin API создаёт других пользователей, максимум 10.

- Минимальная страница: вход, создание и редактирование поиска, повторное обновление с cooldown, список результатов, подробности. Данные сохраняются после перезапуска.

**Drom и Auto.ru подключены в Phase 4** через публичные HTML-страницы. Демонстрационный источник выключен в рабочем приложении. Avito остаётся отключённым: проверяемый контракт выдачи пока не получен. Объявления объединяются в персональные кластеры, доступны ручные merge/reject/split. В Phase 5 включено автообновление по расписанию; интервал и пауза настраиваются в каждом поиске.

## Запуск через Docker Compose

Нужен работающий Docker с Linux containers. Из корня проекта:

```powershell
Copy-Item .env.example .env
```

В `.env` задайте случайный `POSTGRES_PASSWORD` (удобно использовать hex без спецсимволов URL). Для поиска включите `DROM_ENABLED=true` и `AUTO_RU_ENABLED=true`. Остальные значения подходят для локального запуска. Затем:

```text
docker compose up --build -d
docker compose exec backend python -m app.auth.cli admin
```

Введите пароль admin дважды. CLI не создаст второго администратора поверх существующего. Для автоматизации поддерживается `--password-stdin`, пароль читается из стандартного ввода, а не из аргументов команды.

Откройте [http://localhost:8080](http://localhost:8080). PostgreSQL не публикует порт наружу, веб-порт привязан к loopback. При изменении порта обновите `WEB_PORT` и `APP_ORIGIN` согласованно. Для доступа друзей используйте защищённое окружение/HTTPS и `COOKIE_SECURE=true`.

Compose сначала ждёт PostgreSQL, затем выполняет единственный migrate job и запускает API/worker. Для повторного старта достаточно `docker compose up -d`. Остановка: `docker compose down` (без `-v`, данные сохраняются).

```text
docker compose run --rm migrate
docker compose logs --tail=50 worker backend
docker compose exec backend alembic current
```

В `frontend`:

UI доступен на [localhost:8080](http://localhost:8080), Vite перенаправляет `/api` на локальный backend. В Linux/macOS замените `.venv/Scripts/` на `.venv/bin/`.

## Резервная копия и проверка восстановления

Из корня проекта, с настроенным `DATABASE_URL` в `.env` и совместимыми pg_dump/pg_restore. Ниже проверенный нативный путь PostgreSQL 17.11 этой машины; в другом окружении замените `--pg-bin` или добавьте утилиты в PATH и уберите этот параметр. В Python-образ backend эти утилиты не включены.

```text
.venv/Scripts/python.exe -m app.backup create --file .local/backups/manual-01.dump --pg-bin .local/postgresql/pgsql/bin
.venv/Scripts/python.exe -m app.backup verify --file .local/backups/manual-01.dump --database findcar_restore_manual_01 --pg-bin .local/postgresql/pgsql/bin
```

Для каждой копии выбирайте новое имя файла: перезапись запрещена. Храните вместе архив и автоматически созданный `.dump.json`. Архив содержит приватные данные и не зашифрован. Копия согласована с одним снимком БД; verify проверяет SHA-256 архива и содержимое всех таблиц после восстановления. Роль БД должна иметь право создать временную БД.

Проверка создаёт только новую БД с префиксом `findcar_restore_` и удаляет её после сравнения. Существующая БД, включая рабочую, не перезаписывается. Это проверка восстановления, а не команда замены рабочей БД. Финальная копия Phase 6 успешно восстановлена и сверена: 22 таблицы, 139 строк.

## Адаптеры и диагностика

Интерфейс — `backend/app/sources/base.py`, выбор адаптера — `registry.py`. `MockSourceAdapter` использует упакованный `backend/app/sources/mock/listings.json`; происхождение fixtures описано в `backend/tests/fixtures/mock/README.md`. Парсинг mock не обращается в сеть. URL `example.invalid` обозначает демонстрацию и не выводится как ссылка на реальную площадку.

`MOCK_SCENARIO`: `normal`, `dedup`, `empty`, `price_drop`, `removed`, `unavailable`, `rate_limited`, `auth_required`, `parser_error`. После изменения настройки перезапустите worker, затем выполните ручное обновление. `MANUAL_REFRESH_COOLDOWN` по умолчанию 300 секунд. Сценарий `empty` не снимает прежние объявления. `removed` — явное подтверждённое состояние фиктивной карточки. Ошибка не обнуляет последний успешный результат.

Новый источник: отдельный пакет transport/parser/normalizer, реализация CarSourceAdapter, регистрация, явные capabilities, обезличенные fixtures и offline-тесты. Подключать по одному. Ни API, ни сервис ingestion не должны содержать CSS selectors или параметры площадок. Фотографии Drom/Auto.ru загружаются только с проверенных хостов через ограниченный image transport; остальные адреса отклоняются.

Если результаты не обновляются: проверьте `/api/ready`, отметку worker в интерфейсе, `/api/sources/health` после входа и логи worker. Job хранит error_code, количество результатов, предупреждения и lease. После падения worker просроченное задание забирается заново; запись результата требует актуального lease_token. По умолчанию максимум три исполнения, включая восстановление аренды и повторные попытки временных ошибок. `not_before` и общая пауза источника сохраняются в БД; перезапуск не обнуляет их. В интерфейсе показывается время следующей попытки.

При сломанном парсере добавьте минимальный обезличенный fixture с ожидаемым исходом, воспроизведите offline и исправьте parser. Не маскируйте ошибку как пустую выдачу. В логах fetch есть source, saved_search_id, request_type, duration_ms, result_count и status; passwords/cookies не логируются.

Логи worker также содержат job_id/run_id, попытку, причину запуска, версии парсеров и предупреждения. Для исключений сохраняются класс, файл и строка без исходного текста исключения. Ответ API содержит X-Request-ID, по которому можно найти диагностическую запись ошибки БД.

## Границы реализации и следующие этапы

Архитектурные документы описывают целевую схему, которая шире текущего MVP. Сейчас реализованы постоянные сохранённые поиски (разовый `/api/search` с TTL отложен), пагинация результатов и ограниченная история. Email/invites остаются следующими этапами; избранное, скрытие, заметки, fingerprints, duplicate tables и сохранение состояния при merge/split реализованы. CLI создаёт первого admin, затем закрытый `POST /api/admin/users` принимает username/password при admin-сессии, правильных Origin и X-CSRF-Token. Отдельного admin UI пока нет.

Планировщик встроен в отдельный worker-процесс и автоматически обновляет включённые поиски. Lease длиннее общего deadline задания на 30 секунд; задания ограничены по времени. Source-wide бюджеты, ограничение одновременных заданий и паузы сохраняются в PostgreSQL. SQLAlchemy 2 используется через Core, без дополнительных ORM-сущностей поверх той же схемы.
