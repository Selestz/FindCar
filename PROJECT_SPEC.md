Ты — senior full-stack engineer и архитектор. Нужно спроектировать и реализовать приватный веб-сервис — агрегатор объявлений о продаже автомобилей из трёх источников:



\* Avito Авто

\* Auto.ru

\* Drom



Сервис предназначен только для личного использования и небольшого круга друзей, максимум примерно 10 пользователей. Это НЕ публичный поисковик и НЕ задача по копированию всей базы этих сайтов.



Главная идея: пользователь задаёт поиск автомобиля один раз, сервис выполняет эквивалентный поиск сразу на трёх площадках, нормализует результаты, объединяет объявления об одном и том же физическом автомобиле и показывает их в единой ленте.



Также пользователь может сохранить поиск, после чего сервис периодически проверяет только этот конкретный поиск и сообщает о новых объявлениях, изменениях цены, снятии/возвращении объявления и возможном перевыставлении того же автомобиля.



\---



\# 1. Основная концепция



Это должен быть не crawler всей России, а lightweight metasearch/monitoring service.



Не нужно:



\* обходить все автомобили на площадках;

\* копировать полные базы площадок;

\* скачивать все фотографии;

\* пытаться заменить собой Avito/Auto.ru/Drom;

\* хранить телефоны продавцов или другие лишние персональные данные;

\* обходить CAPTCHA, антибот-защиту или другие ограничения запрещёнными/агрессивными методами.



Нужно:



1\. Получить поисковый запрос пользователя.

2\. Преобразовать его в запросы для каждого источника.

3\. Получить несколько первых страниц результатов.

4\. Нормализовать объявления.

5\. Найти одинаковые физические автомобили.

6\. Склеить их в одну карточку.

7\. Показать основные данные.

8\. Показать главное фото.

9\. Показать описание/комментарий продавца.

10\. Дать прямые кнопки перехода на исходные объявления.

11\. Сохранить минимальный набор данных для отслеживания истории.

12\. Периодически обновлять сохранённые поиски.



Проект должен проектироваться так, чтобы изменение HTML одного сайта не ломало остальную систему.

Ядро приложения НЕ должно знать:

\* структуру их HTML;

\* названия внутренних query parameters;

\* формат внутренних API.



Вся эта логика должна находиться внутри соответствующего adapter.



Если один источник перестал работать, два остальных должны продолжать работать.



Для каждого источника сначала исследуй наиболее устойчивый и допустимый способ получения данных:



1\. официальный/public API или официальный интеграционный механизм, если он подходит;

2\. доступные серверные JSON-запросы, если их использование допустимо;

3\. обычный HTML parsing;

4\. browser automation только если действительно необходимо.



Не используй Playwright просто потому, что так проще.



Не реализуй обход CAPTCHA, fingerprint spoofing, proxy rotation и прочую гонку с антиботом.



Если источник блокирует автоматизированный доступ, архитектура должна корректно сообщать:



SOURCE\_UNAVAILABLE / RATE\_LIMITED / AUTH\_REQUIRED



вместо бесконечных повторных запросов.



Все особенности текущего доступа к трём источникам задокументируй в:

\# 7. Дедупликация БЕЗ VIN



VIN считать приятным дополнительным сигналом, но система НЕ должна зависеть от VIN.



На практике VIN часто скрыт или доступ к нему платный.



Основой дедупликации должны быть фотографии + характеристики автомобиля.



Реализуй двухэтапный matching pipeline.



\## Этап A — candidate generation



При появлении нового объявления НЕ сравнивай его со всеми автомобилями в БД.



Сначала выбери небольшой набор потенциальных кандидатов по:



\* make;

\* model;

\* generation;

\* year ± допустимое отклонение;

\* engine;

\* кузов;

\* mileage с разумным допуском;

\* регион/город;

\* цвет, если есть.



Например:



Porsche Panamera 4S

2011

143 000 км

Москва



можно сравнивать с Panamera подходящего поколения примерно 2010–2012 и близким пробегом.



\## Этап B — similarity score



Рассчитывай score из нескольких независимых сигналов.



Самые важные:



\### 1. Фотографии



Это основной сильный сигнал.



Один продавец часто загружает одну фотосессию на три площадки, но:



\* сайты меняют resolution;

\* пережимают JPEG;

\* могут добавлять watermark;

\* меняют порядок фотографий;

\* иногда немного crop'ают изображение.



Поэтому обычный SHA256 картинки не подходит.



Для фотографий реализуй perceptual fingerprints:



\* pHash/dHash или аналог;

\* архитектуру сразу подготовь под image embeddings.



Необходимо сравнивать несколько фотографий, а не только первую.



Если совпали несколько фотографий одной фотосессии — это должен быть очень сильный сигнал.



На первом этапе можно использовать perceptual hash.



Позже должна быть возможность добавить CLIP/OpenCLIP embeddings без переписывания дедупликации.



\### 2. Основные характеристики



Сравнивать:



\* make

\* model

\* generation

\* year

\* engine

\* power

\* gearbox

\* drive

\* body

\* color



\### 3. Пробег



Не требовать точного равенства.



143 000 км и 145 200 км могут быть одной машиной.



Допуск должен быть configurable.



\### 4. Описание



Описание — дополнительный, но не решающий сигнал.



Использовать fuzzy text similarity.



Учитывать, что продавец может немного изменить текст при публикации на другой площадке.



\### 5. Редкие характеристики



Если доступны:



\* необычный цвет салона;

\* панорама;

\* конкретная комплектация;

\* редкий двигатель;

\* необычные диски;

\* другие структурированные характеристики.



Это дополнительные сигналы.



\### 6. Цена



Цена является слабым сигналом.



Одна машина может стоить:



Avito: 1 690 000

Auto.ru: 1 740 000

Drom: 1 700 000



Не использовать цену как обязательное условие совпадения.

\# 8. Решение о дубле



Similarity engine должен возвращать не просто boolean, а:



DuplicateScore {

total\_score

confidence

individual\_signals

explanation

}



Например:



photo\_similarity = 0.94

matching\_images = 5

mileage\_similarity = 0.97

year\_match = true

color\_match = true

description\_similarity = 0.72



total = 0.91



Правила должны быть configurable.



Пример первоначальной логики:



> = 0.88:

> автоматически объединить



0.68–0.879:

possible duplicate



< 0.68:

считать разными



Порог не хардкодить глубоко в коде.



КРИТИЧЕСКИ ВАЖНО:



Никогда не объединять автомобиль автоматически только потому, что совпали:



марка + модель + год + цвет.



Например чёрных BMW 320i одного года может быть огромное количество.



Для auto merge должен существовать хотя бы один сильный индивидуализирующий сигнал:



\* несколько совпадающих фотографий;

\* очень необычный набор характеристик;

\* другой достаточно надёжный fingerprint.

\# 12. Работа с фотографиями



Пользователь хочет видеть фотографию автомобиля, но не нужно создавать собственный полный фотобанк.



Стратегия:



\* получить URL фотографий;

\* использовать первые несколько изображений для вычисления fingerprints;

\* хранить fingerprints;

\* полные скачанные изображения после обработки можно удалять;

\* сохранить URL оригинала;

\* для UI нужна главная фотография.



Так как source URL может перестать работать, предусмотреть configurable thumbnail cache.



Для приватного приложения допустимо локально хранить ОДНУ уменьшенную thumbnail на объявление, например максимум 512–768 px, если это необходимо для стабильного UI.



Не сохранять полный комплект фотографий без необходимости.



Создай storage abstraction, чтобы thumbnail можно было хранить:



\* локально;

\* позже в S3-compatible storage.

\# 14. Мониторинг



Worker периодически выполняет сохранённые поиски.



При каждом проходе:



1\. Выполнить поиск по каждому enabled source.

2\. Нормализовать найденные объявления.

3\. Upsert по source + source\_listing\_id.

4\. Обновить last\_seen.

5\. Выполнить deduplication.

6\. Создать snapshots только при изменении значимых данных.

7\. Определить новые объявления.

8\. Определить снижение/повышение цены.

9\. Определить исчезнувшие объявления.

10\. Найти возможные relist.

11\. Создать события.



Создай таблицу/модель Event.



Типы:



NEW\_LISTING

PRICE\_DROP

PRICE\_INCREASE

LISTING\_REMOVED

LISTING\_RETURNED

PROBABLE\_RELIST

POSSIBLE\_DUPLICATE



Это позволит позже добавить Telegram/email/push уведомления.



На первом этапе достаточно notification center внутри сайта.



Архитектуру уведомлений сделать расширяемой.

\# 23. Source rate limiting



Каждый adapter должен иметь свой rate limiter.



Настройки должны задаваться через config/environment.



Не делать десятки одновременных запросов к одному сайту.



Использовать:



\* разумный concurrency limit;

\* retry с exponential backoff для временных ошибок;

\* timeout;

\* max retry;

\* clear failure state.



Не делать aggressive scraping.



Добавить небольшой scheduler jitter, чтобы все saved searches не стартовали одной огромной пачкой каждую ровную минуту.



\---



\# 24. Parser robustness



Не пиши parser, который существует только как 300 CSS selectors в одном файле.



Для каждого источника:



\* отдельно transport/fetching;

\* отдельно parsing;

\* отдельно normalization.



Добавить fixtures с сохранёнными примерами ответов/HTML.



Parser tests должны работать без обращения к реальным сайтам.



Например:



tests/fixtures/avito/

tests/fixtures/auto\_ru/

tests/fixtures/drom/



При изменении сайта должно быть легко:



1\. положить новый fixture;

2\. воспроизвести ошибку;

3\. поправить parser;

4\. прогнать test.

\# 25. Observability

Structured logging.

status

Сделать health endpoints.

Предусмотреть sanity checks.
